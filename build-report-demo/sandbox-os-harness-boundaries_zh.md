# 一份统一安全策略，三个执行面：Sandbox、OS Harness 与 Gateway

> 一份策略定义安全边界，三个执行面共同落地：Sandbox 管运行环境，OS Harness 管 OS 操作，Gateway 管外部请求与凭据使用；按能力分配执行责任，按证据展示实际覆盖。

本文面向方案汇报，说明三类执行机制的关系，以及一份 Policy 如何对应三者的边界。示例采用 build-report 的完整“构建、保护、上报”场景，属于架构与执行分工说明，不是运行验收报告。

具体的 R1–R4 Cedar 正文、环境 A／B／C 映射、YAML 示意及派生配置来源追踪，集中在[统一 Policy 组织样稿](unified-policy-organization-example_zh.md)。本文保留执行边界与验收口径，不重复维护完整样稿。

**讨论前提：按 schema 已统一、执行适配完成后的目标架构说明。** 仓库仍保留 [seccore.cedarschema](../src/agent-sec-core/v2/crates/asc-policy-cedar/schema/seccore.cedarschema) 与 [seccore-v2.cedarschema](../src/agent-sec-core/v2/crates/asc-policy-cedar/schema/seccore-v2.cedarschema)：前者定义文件、进程与整体网络权限，后者增加 HTTP 请求类型和 `network.send`。当前生成提示已按 R 编号组织正文（编号只写在注释里），混合策略转译与跨端规则追踪仍需适配；本文不是这些改造已完成的声明。具体实现差异见组织样稿第 6 节。

## 1. 一份 Policy，三个执行视图

目标方案以一份统一源策略表达安全要求，由三个执行面按能力承接：

- **Sandbox 类**：包括 bubblewrap、Docker、microVM，负责构造任务的受限运行环境。
- **OS Harness 类**：包括基于 eBPF、Lua LSM 等 OS 底层机制的执行方案，负责在操作系统安全检查点约束任务行为。
- **Gateway 类**：负责经过网关的应用层请求与凭据使用控制，例如检查 GitHub 请求目标，并将 fake token 替换为真实 token 后再发往上游。

三者共同落实同一份策略，不是各自制定一套规则。所列技术类别也不代表所有后端均已接入。

```text
                         任务意图 Intent
                               ↓
                        统一安全 Policy
             本地资源与网络权限 + HTTP 请求与凭据使用规则
                               ↓
                   根据运行环境与能力进行映射
                               │
          ┌────────────────────┼────────────────────┐
          ↓                    ↓                    ↓
    Sandbox Policy      OS Harness Policy     Gateway Policy
    运行环境执行视图      OS 操作执行视图        请求与凭据执行视图

    bubblewrap          eBPF / Lua LSM 等     HTTP 请求匹配
    Docker              OS 底层安全机制        fake → real token
    microVM                                  响应凭据回写保护

    限制工作范围         保护文件操作           限制凭据使用范围
          └────────────────────┼────────────────────┘
                               ↓
                      同一任务的最终保护效果
```

图中三个分支是责任映射，不表示每次操作都依次经过三个执行面。文件删除主要由文件保护路径处理；外部上报则需要网络路径与 Gateway 配合。

这里的 Sandbox Policy、OS Harness Policy 和 Gateway Policy，是**同一源策略的执行投影**，不是三份独立维护的安全政策。执行配置的格式可以不同，但都应追溯到同一个 `policyId + revision`，并明确保护的是哪个任务、进程作用域、资源或请求。

例如，源策略只表达“禁止删除回滚包”，不必把这条要求永久绑定为“仅由 OS Harness 执行”。选择哪个执行端承接，由部署环境、后端能力和保护要求共同决定。

Intent 生成的内容首先是候选，经过确认后才能作为发布输入；不能因为生成成功，就认为策略已经批准或生效。三个执行视图必须源自实际发布的版本，不能一端使用候选、另一端使用人工另写的策略，却仍声称来自同一版本。

### Intent 生成一份还是三份 Policy？

**建议 Intent 生成一份统一源策略，再由执行适配根据运行环境派生三个执行视图，不让 Intent 分别独立生成三套政策。** 源策略回答“安全要求是什么”，执行映射回答“这次由谁、在哪里执行”。

| 对象 | 内容与维护方式 |
| --- | --- |
| 统一源策略 | 集中表达允许、禁止和保护要求；确认后按统一版本发布 |
| 本次执行映射 | 根据后端能力和部署作用域，为每条要求指定一个或多个承接端，并列出缺口 |
| 各端执行配置 | 从同一已发布版本派生，可采用各后端需要的格式，不独立修改业务授权 |

落地时可以输出三个配置文件，也可以通过 API 下发；**物理文件数量不等于独立 Policy 数量**。它们不一定都是 Cedar，也不是必须把源文件裁成三个互不重叠的文本片段。派生配置应保留来源版本与规则对应关系；需要改变安全要求时，先更新源策略，再重新派生。

分别独立生成、维护三份策略，容易出现同一要求条件不一致、只修改其中一份，或各端都以为另一个端负责而漏掉保护的问题。即使生成时参考了环境信息，也不能因为某个执行端不支持，就悄悄删除任务要求；应调整映射或明确报告无法落实。

### 统一 schema、统一 Policy 与执行适配不是一回事

- **schema** 定义能描述哪些对象、动作和上下文，是共同的策略语言，不是授权本身。
- **Policy** 用这套语言表达任务的安全要求，例如允许写产物、禁止删回滚包、允许向指定 Issue 上报。
- **执行适配** 将规则转成各执行端可承接的配置，并报告未承接的要求。仅把两个 schema 文件拼在一起，不会自动完成混合规则转译和三端路由。

| 统一语言中的表达 | 回答的问题 | 本例主要承接端 |
| --- | --- | --- |
| `file.read`、`file.write`、`process.spawn` 等 | 本地资源与进程操作是否允许？ | Sandbox 与 OS Harness 按能力分工 |
| `network.use` | 是否授予整体网络使用权限？ | Sandbox 等网络边界机制 |
| `network.send` + HTTP 条件 + 凭据注解与绑定 | 哪个 HTTP 请求可以使用指定凭据？ | Gateway |

`network.use` 不提供 URL、方法和路径粒度；`network.send` 也不会自动建立可达的网络通道。**能连接，不等于能使用凭据；请求获准，也不等于网络隔离会自动放行。**

真实 token 的值不应进入 Intent、可读策略正文或演示输出。Policy 记录使用条件与凭据引用，受信的凭据存储和绑定负责保存、提供真实值；凭据注入由 Gateway 执行，不是 Cedar 的 `permit` 自己完成替换。

## 2. 三者的边界按执行机制划分，不按规则类型硬切

| 维度 | Sandbox 类 | OS Harness 类 | Gateway 类 |
| --- | --- | --- | --- |
| 核心职责 | 构造受限运行环境 | 在 OS 安全检查点约束操作 | 控制外部请求与凭据使用 |
| 典型机制 | 文件系统布局、namespace、容器、虚拟机 | eBPF、Lua LSM 等底层检查与拦截 | HTTP 代理、请求规则匹配、凭据替换 |
| 典型效果 | 限制资源可见性、访问范围与网络；microVM 隔离 guest 内核 | 拒绝特定对象的读、写、删除等操作 | 限定凭据可用于哪个服务、方法和路径；真实 token 不交给任务 |
| 保护范围 | 实际进入隔离环境的进程及其受约束后代 | 纳入作用域、且经过已覆盖检查点的操作 | 实际经过网关并能被解析、匹配的请求 |
| 不能替代的边界 | 仅靠隔离不自动实现 HTTP 凭据替换 | 不等价于 VM 隔离，也不自动具备 HTTP 请求语义 | 不隔离本地进程，不阻止文件删除，也不能清除已写入的本地日志 |

**不能简单说“Sandbox 只能粗粒度，OS Harness 才能细粒度”。** 不同 Sandbox 的能力不同，精细访问控制也可能由 Sandbox 完成；OS Harness 也不只适合保护单个文件。

三个执行面的部分能力可以重叠，但工作层次与信任边界不同。不能因为都能阻止一次操作，就认为可以完全相互替代。

### 同一段 Cedar 可以同时由 Sandbox 和 OS Harness 执行吗？

**可以。同一条 Cedar 表达的要求，可以同时由两个执行面承接，并不天然专属于其中一个。** 前提是两端适配器都能正确解释相关规则，且实际部署覆盖了要求中的对象、操作和作用域；这不是对现有所有后端的兼容性承诺。

| 统一要求 | Sandbox 可承担的部分 | OS Harness 可承担的部分 | Gateway 可承担的部分 | 关系 |
| --- | --- | --- | --- | --- |
| 禁止删除 `previous.zip`，保留正常写入 | 后端支持精确操作控制时，可承接禁删 | 在已覆盖的操作路径实施删除保护 | 不承接本地删除 | 同一要求可由两端重叠执行 |
| 禁止读取 `deploy.env` | 在其作用域内隐藏资源或拒绝读取 | 在其作用域内拦截读取 | 不替代本地读取保护 | 同一要求可由两端重叠执行 |
| GitHub 凭据仅用于指定上报接口，真实值不交给任务 | 隔离真实凭据并配合限制出口 | 可补充凭据文件读取保护 | 按请求匹配条件注入真实 token | 多端分工协作，不是三端执行相同动作 |

前两行体现“同一要求、多端执行”，第三行体现“一个目标、多端协作”。一项业务要求也可能需要多条 Cedar 语句及配套部署约束，不能假定“一项要求 = 一条语句 = 一个执行端”。

执行投影需要保留相关规则组合的语义，不能只按注释剪切文本。例如允许写产物与禁止删回滚包需要共同落实；某端承接允许范围，另一端承接禁止操作时，不能因为前者放行就忽略后者的约束。

### 为什么“都能禁删”不意味着两者等价

“禁止删除某个文件”可能有多种实现：

- 将所在目录设置为只读，可以阻止删除，但往往同时禁止正常写入。
- 支持独立操作权限的 Sandbox，可以分别限制写入和删除，具体粒度取决于后端。
- OS Harness 可以在删除、重命名等检查点实施对象级约束，前提是对应操作路径确实被覆盖。

比较时不只看“删除是否失败”，还要看**是否在同一对象范围内阻止了危险操作，同时保留了业务需要的合法操作**。为了实现“禁删”而把正常构建写入也封掉，不能算完整满足任务要求。

### bubblewrap、Docker、microVM 的边界不同

| 类型 | 隔离特点 | 需要明确的边界 |
| --- | --- | --- |
| bubblewrap | 通过 namespace、挂载布局及可配置的过滤机制构造沙箱 | 共享宿主内核；保护强度取决于实际参数与暴露资源 |
| Docker | 组合容器运行时、namespace、cgroups、capabilities 及安全配置 | 常规 Linux 容器共享宿主内核；特权模式、宿主挂载和 socket 暴露会改变边界 |
| microVM | 通过独立 guest 内核和虚拟化构造执行环境 | 增加内核隔离边界，但仍需考虑 VMM、虚拟设备与共享通道 |

不能仅根据产品名称判断哪个更安全，也不能把宿主上的 eBPF 访问控制等同于独立 guest 内核。

任务运行在 microVM 内时，宿主 OS Harness 通常不能直接识别 guest 内部的 `previous.zip` 删除语义。该要求需要 guest 内执行端，或其他能识别相应文件操作的机制承接。Gateway 可以部署在 guest 外承接上报，但必须配置受控网络路径及相应的 HTTPS 信任关系。**执行端部署在哪一层，也是策略映射的一部分。**

### Gateway 管凭据怎么用，不只是管网络通不通

“允许连接 GitHub”与“允许使用这个 GitHub token 向 Issue #42 提交评论”是不同权限。Gateway 可以在能解析的 HTTP 请求上按主机、协议、方法和路径匹配，再决定是否替换凭据；单纯开放 IP 或端口不能表达同样的要求。

完整保护还需要两类配合：

1. **受控出口**：Sandbox 或其他具备能力的网络机制保证请求经由 Gateway，不能只设置一个可以被任务忽略的代理环境变量。本文不把网络阻断算作现有 ActPlane 文件保护通道已具备的能力。
2. **受控凭据**：任务只能拿到 fake token；真实 token 由受信组件持有，且不能通过文件、环境变量、调试接口等旁路被任务读取。

Gateway 的凭据规则不应被泛化为完整的网络防火墙。[现有 Gateway 计划](../src/agent-sec-core/v2/crates/asc-gateway-plan/src/plan.rs)约束受管 fake token 的使用，不携带受管凭据的请求可在安全检查后原样转发。因此，“其他所有外联都拒绝”需要额外的出口与请求控制，不能仅凭 token 替换规则就宣称成立。

同样，允许某个上报 URL 不代表已经验证请求正文只能包含构建摘要，也不代表任意编码、任意通道的数据泄露都能被发现。

## 3. 用 build-report 任务说明一份策略如何分工

完整业务目标是在 `/srv/br-demo` 构建项目，将产物写入 `releases/`、报告写入 `out/`，保护回滚包和模拟凭据，并将构建摘要上报到 GitHub Issue #42。

**区分现状与目标：** [现有任务文本](task.txt)仍是本地验收：只写 `releases/`、`out/`，禁止联网，不上报；[上报脚本](skill/build-report/scripts/report.sh)保留了 R3 的 Authorization 头泄露风险。下面按启用 Gateway 的完整上报场景说明目标分工，不表示现有 `task.cedar` 已允许上报，也不改变本地验收版的禁网要求。

源策略按安全要求组织，执行归属另行映射：

- **R1：构建写入范围**——只允许写 `releases/`、`out/`。
- **R2：回滚包删除保护**——禁止删除 `releases/previous.zip`，不额外禁止普通原地写入。
- **R3：GitHub 凭据使用限制**——指定凭据仅用于向 Issue #42 提交评论；任务只持 fake token，匹配请求由 Gateway 替换为真实 token。
- **R4：敏感文件读取保护**——禁止读取模拟凭据文件 `project/deploy.env`。

完整策略还需表达任务确认的基础读取、程序启动等授权，配套执行还需隔离真实凭据并落实受控出口；不能把四项核心规则当成完整启动策略。具体 Cedar 与 HTTP 匹配条件见[组织样稿](unified-policy-organization-example_zh.md)。

上述网络要求是“受控外联”，不是“一边完全禁网、一边允许上报”。Sandbox 必须为 Gateway 通道提供必要可达性，同时由相应网络机制限制旁路；仅有粗粒度 `network.use` 或 HTTP `network.send` 规则，不能单独证明这条出口约束已经实现。

| 风险或要求 | Sandbox Policy | OS Harness Policy | Gateway Policy |
| --- | --- | --- | --- |
| R1：依赖脚本越界写 shell 配置 | 限定写入范围，阻止范围外写入 | 本例不重复承担 | 不处理本地文件写入 |
| R2：清理脚本删除 previous.zip | 允许 releases/ 正常工作；本例不精确承接 delete-only | 承担回滚包删除保护 | 不处理本地文件删除 |
| R3：上报脚本打印 Authorization 头 | 隔离真实凭据，配合限制网络出口 | 可补充真实凭据文件访问保护，但不替代 token 替换 | 任务使用 fake token，匹配请求才注入真实 token |
| R4：模拟凭据 deploy.env 禁读 | 本例不靠宽范围读取权限单独保证 | 承担精确文件读取保护 | 不替代本地文件保护 |
| R3 配套：受控出口与指定接口上报 | 提供受控 Gateway 通道 | 本例的文件保护通道不承担 HTTP 控制 | 按主机、HTTPS、POST 和路径约束凭据使用 |

R1–R3 安全要求分别对应 [build-report Skill](skill/build-report/SKILL.md) 的三类风险；R4 是本文与组织样稿对本地凭据禁读要求的编号，不表示 Skill 新增了风险编号，也不与 README 的 Case 编号混用。表格描述一种目标责任分配，不代表已经下发或验证，更不是规则的永久归属。

其中最直观的关系是：

> Sandbox 让任务在规定范围内工作，OS Harness 保证它不能删除回滚包，Gateway 让它能上报却拿不到真实 GitHub token。三个执行面落实的是同一份任务安全要求。

凭据禁读还说明了调用路径的边界：如果只把 shell 命令放进 Sandbox，运行在其外的原生文件工具不会自动被这个 Sandbox 覆盖。OS Harness 若已覆盖实际执行读取的进程及相应检查点，可以在该操作发生时拦截；不能因此推断它自动覆盖所有工具、代理服务或远程操作。

### R3：脚本照常打印，但打印不到真实 GitHub token

`report.sh` 从 `GITHUB_TOKEN` 取值，将 Authorization 头同时打印到终端和 `out/debug.log`，再调用 GitHub API。风险不在于“有没有日志”，而在于任务持有的是不是真实 token。

目标链路如下，尖括号内容均为示意占位值：

```text
受信凭据存储：保存 <real-token>，不提供给 Agent 或脚本
                       │
任务环境：GITHUB_TOKEN=<fake-token>，绑定受限作用域
                       │
report.sh 打印 Authorization: Bearer <fake-token>
                       │
                       ↓
Gateway 收到携带 fake token 的请求
  检查：任务作用域、凭据绑定、HTTPS、host、POST、path
  不匹配 → 拒绝受管凭据的使用，不注入真实 token
  匹配   → Authorization: Bearer <real-token>
                       │
                       ↓
             GitHub 完成受允许的上报
                       │
                       ↓
Gateway 按配置处理响应中可识别的凭据回显
                       │
                       ↓
任务收到响应，不应获得真实 token
```

这里的 fake token 不是随便填写的无效字符串，而是被网关识别并绑定到凭据和任务作用域的替身；它在获准作用域内仍可触发凭据使用，需要管理其生命周期和暴露范围。

**Gateway 解决的是“真实 token 不进入任务”，不是“事后清除日志里的 token”。** 如果仍把真实 token 放入脚本环境，它在网络请求发出前就会被打印，Gateway 无法撤回该泄露。

落地和验证需同时关注：

- 真实 token 不出现在任务可读文件、环境变量、命令行及可读调试接口中。
- Gateway 只对获准请求替换凭据，不能向任意主机或路径注入。
- 响应回显保护需要显式启用并验证；它只覆盖实现支持的形式，不代表任意变形、编码内容都能清洗。
- Gateway 自身日志、抓包和审计记录也不能泄露替换后的真实值。

### 本地文件保护的两个细节

- **普通原地写入不等于替换文件。** 通过临时文件加 rename 覆盖目标，可能触发删除保护；不能承诺任意形式的“覆盖保存”都成功。单独禁删也不等于文件内容不可篡改。
- **读取上限与精确禁读需要区分。** 当前 [task.cedar](policies/task.cedar) 采用整个文件系统的读取上限（由程序生成的基础授权给出，[task.txt](task.txt) 不写），再按 task 对 `deploy.env` 实施精确禁读；不再以读取目录白名单作为本地任务要求。宽读取上限不是最小读取白名单，实际读取仍受命令申请、执行投影与保护作用域约束；真实 Gateway 凭据必须另行隔离，不能因 `deploy.env` 被保护就认为所有凭据都安全。

### 更换执行后端，不必重新定义业务规则

如果未来选择的 Sandbox 能精确执行回滚包禁删要求，可以由它承接；如果 Sandbox 和 OS Harness 都能执行，也可以叠加保护。业务规则不因此改变，变化的是执行映射。Gateway 的请求匹配与凭据替换仍需具备对应能力的执行端承接。

以 R2 为例，同一源规则可以在环境 A 由 OS Harness 承接，在具备精确禁删能力的环境 B 由 Sandbox 承接，在环境 C 由两端共同保护。完整环境对照和前置条件见[组织样稿](unified-policy-organization-example_zh.md)第 3 节。

任务的业务要求和资源范围不变时，更换后端通常只需调整映射并重新验证；如果任务范围或授权需求本身改变，则应修订源策略版本，不能在派生配置里偷偷放宽。两端都无法满足要求时，明确列为缺口，不删除源规则。

需要坚持三点：

1. 不能固定认为 `permit` 都属于 Sandbox、`forbid` 都属于 OS Harness；Gateway 的凭据授权也可以通过 `permit` 表达。
2. 三端约束是叠加，不是权限相加。Gateway 批准请求不能绕过网络隔离，Sandbox 放行连接也不能绕过 Gateway 的凭据规则。
3. 未被任何执行端承接的要求必须列为缺口；一个执行端不处理某条规则，必须有明确的责任交接，不能默默丢弃。

### Cedar 按安全要求组织，执行归属单独展示

目标组织方式是：**源策略按 R1–R4 安全要求分组，本次执行映射引用源规则，派生视图再按 Sandbox／OS Harness／Gateway 展示。** 规则标识用于追踪要求，不把执行端写成永久归属；一项要求可以映射到多个执行端。

[现有生成提示](../src/agent-sec-core/v2/crates/asc-intent/prompts/policy-generation.md)与留档策略已改为：基础授权由程序固定生成并置于正文前，模型先写 task 写明的写入范围（`goal`），再把 task 所列各点按顺序编为 R1、R2…分块（本地任务是 R1 禁删、R2 禁网、R3 禁读，与本文 R1–R4 的样稿编号不同），每条语句用 `@id` 标明所属要求（文件保护转译器接受 `@id`，拒绝其他注解）；执行端仍按规则形状各取所需，生成时以 `COVERAGE` 预览每项要求能由谁承接，不是本文第 4 节那种显式执行映射。目标源策略不再通过追加固定 `[G*]` 区来划定互斥归属；S/H/G 名称可以保留在执行视图或责任展示中。改变注释并不会自动改变转译器，混合策略适配仍需实现。

同一要求出现在两个派生配置中，是有意的**执行重叠**，不是两套独立安全政策。变化集中在源策略或环境映射中，派生配置随之更新；具体的规则标识、YAML 映射与来源追踪见[组织样稿](unified-policy-organization-example_zh.md)第 2、4、5 节。

## 4. 同时展示策略覆盖与实际生效

统一策略的价值不仅是“一个文件”，还在于能把每条要求的责任与结果对应起来。

| 层次 | 回答的问题 | 不能据此直接推断的结论 |
| --- | --- | --- |
| 已表达 | 统一策略中是否有这条安全要求？ | 有规则不等于有执行端支持 |
| 已映射 | 是否已转成执行端可承接的规则或配置？ | 转译成功不等于已经下发 |
| 已应用 | 是否已在目标作用域加载？ | 加载成功不等于实际阻断已验证 |
| 已验证 | 是否有针对该要求的实际测试证据？ | 单个样例通过不等于所有路径都覆盖 |

仅在图中指定“由 OS Harness 或 Gateway 承担”，属于责任分配；如果没有真实转译结果，不能标为“已映射”。同样，文件保护的 `Binding READY` 不能证明 Gateway 规则已加载，更不能代替 token 替换验证。每个执行面都需要自己对应的应用回执与行为证据。

对一条规则由两端共同执行的情况，还需要区分“要求已得到保护”与“两端均已验证”：

- 两端均应追溯到同一 `policyId + revision` 及对应源规则，分别显示应用和验证状态；不能一端成功，就将另一端也标为成功。
- 组合测试中若操作已被前一个执行端拒绝，后一个执行端可能根本没有收到操作，不能据此证明两端都成功拦截。验证双重保护需在受控测试环境中获得各端证据，同时检查合法操作仍可完成。
- 汇总时，一项要求被两个端执行仍算一项安全要求；报告可以分别统计要求覆盖数与执行端验证数，不能通过复制规则虚增覆盖率。
- 若本次要求双重保护，一端失败就不能声称双重保护已完成；若允许单端承接，也需确认该端独立覆盖完整要求，并明确另一端的状态。

### 汇报中的覆盖表

下面是展示格式示例，不是本机运行结果；每一项都应由实际证据填入。

| 统一策略要求 | 本次执行责任 | 策略覆盖 | 实际生效状态示例 |
| --- | --- | --- | --- |
| R1：限定写入范围 | Sandbox | 已表达、已映射 | 已应用，越界写入样例验证通过 |
| R2：禁止删除 previous.zip | OS Harness | 已表达、已分配责任 | dry-run，仅预览，未下发 |
| R4：禁止读取 deploy.env | OS Harness | 已表达、已分配责任 | 等待下发与读取阻断验证 |
| R3 配套：上报经过受控出口 | Sandbox + 网络执行机制 | 已分配责任 | Gateway 可达性与旁路阻断待验证 |
| R3：GitHub 凭据仅用于指定接口 | Gateway | 已表达、已分配责任 | HTTP 匹配与越权请求拒绝待验证 |
| R3 配套：真实 token 不进入脚本日志 | Gateway + 凭据隔离 | 规则与托管要求已列示 | fake → real 替换、响应回显与日志检查待验证 |

这张表同时说明三个边界：

- **策略边界**：任务应该受到哪些限制。
- **执行边界**：本次由哪种机制、在哪个作用域承担限制。
- **生效边界**：哪些已经落实，哪些仍有缺口。

### previous.zip 在不同状态下怎么说明

| 状态 | 正确解释 |
| --- | --- |
| dry-run，仅预览 | 禁删要求已表达，执行计划可见，但本轮未下发；没有运行时保护证据 |
| 下发失败 | 禁删要求仍在统一策略中，但目标作用域未成功应用该版本；保护未获确认 |
| 已加载，未测试 | 收到应用就绪回执，但尚未验证删除确实被拒绝 |
| 阻断验证通过 | 目标作用域内发起删除被拒绝，文件保持完整，并有对应证据；合法写入语义需另行验证 |

**没有发起删除、演示程序没有释放删除命令、或者文件仍然存在，都不能单独证明 OS Harness 已成功拦截。**

### R3 在 Gateway 不同状态下怎么说明

| 状态 | 正确解释 |
| --- | --- |
| dry-run，仅预览 | 已展示请求匹配与替换计划，尚无真实转发和替换证据；不能宣称 R3 已解决 |
| 下发失败、绑定缺失或网关不可用 | 当前上报保护未就绪；不得改成给脚本真实 token，或允许绕过网关直连 |
| 已加载，未测试 | 网关计划已应用，但请求是否经过网关、凭据是否正确替换及日志是否安全仍待验证 |
| 验证通过 | 任务仅持 fake token，受控测试上游验证注入正确；错误主机、方法、路径的凭据请求被拒绝，任务与网关日志、响应均完成相应检查 |

验证可以使用受控测试端和测试凭据，不需要向真实 Issue 发评论，也不应在验收输出中打印真实 token。只看到 HTTP 成功，不能证明凭据没有泄露；只看到日志中是 fake token，也不能证明请求已经经过 Gateway 或正确完成替换。

如果关键保护尚未落实，应明确展示“安全验收未完成”；演示流程完成不能被表述为任务已获得完整保护。对必须具备的保护，执行编排应在其应用就绪前阻止相关危险操作开始，不能静默降级。停用 Gateway 的本地验收仍维持禁网，不与完整上报场景混用。

因此，面向管理者的最终结论是：

> **Intent 生成一份统一源策略，根据运行环境派生三个执行视图：Sandbox 限定运行环境，OS Harness 约束本地操作，Gateway 控制外部请求与凭据使用。一条规则可以由一个执行面承担，也可以由多个执行面共同保护；三者同源、按能力分工，逐条展示实际生效状态。**
